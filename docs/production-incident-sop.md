# 生产问题预警、排查与权限协同 SOP

> 初版负责人：Isaac  
> 协同：竹舟、展翅高飞、技术团队  
> 目标：任何教育场景、大型活动、线上生产问题都能快速发现、快速排查、快速同步、快速恢复，避免因为余额、权限、信息遗漏或沟通断层扩大事故。

## 1. 适用范围

本 SOP 覆盖以下线上问题：

- 站点不可访问、502/504、白屏、登录异常
- 接口 500/4xx 激增、核心流程失败
- 数据库、Redis、Agent、Java 后端、AI 服务异常
- 云服务余额不足、API Key 失效、额度耗尽、自动续费失败
- CI/CD 部署失败、镜像拉取失败、容器重启、健康检查失败
- 域名、DNS、CDN、证书、对象存储、邮件服务异常
- 大型教育活动/课程直播/活动报名/创作任务期间的突发故障
- 因权限缺失导致排查或恢复被阻塞

## 2. 分级标准

| 等级 | 定义                                                                | 响应目标                                      | 通知方式                      |
| ---- | ------------------------------------------------------------------- | --------------------------------------------- | ----------------------------- |
| P0   | 生产主站不可用、核心支付/登录/创作/活动入口不可用、大面积用户受影响 | 5 分钟内响应，15 分钟内给出初步原因或止血方案 | 群消息 + 邮件 + 电话/即时联系 |
| P1   | 核心功能部分不可用、部分用户无法完成流程、错误率明显升高            | 10 分钟内响应，30 分钟内给出处理进展          | 群消息 + 邮件                 |
| P2   | 非核心功能异常、单点功能降级、可绕过                                | 当天响应并安排修复                            | 群消息，必要时邮件            |
| P3   | 体验问题、文案/样式/轻微数据问题                                    | 排期处理                                      | 任务系统/群同步               |

## 4. 技术排查 SOP

### 4.1 先做 5 件事

1. 确认影响范围：单用户、单页面、单接口、单环境，还是全站。
2. 确认最近变更：是否刚部署、改配置、改 DNS/CDN、改密钥、改余额策略。
3. 确认系统健康：Web、Server、Agent、Java、PG、Redis、对象存储、AI Provider。
4. 先止血：回滚、重启、切流、降级、关闭非核心入口、暂停活动入口。
5. 同步信息：P0/P1 必须群消息 + 邮件，避免只有口头或私聊记录。

### 4.2 502 / 504 排查

检查顺序：

1. 访问站点和健康检查接口。
2. 查网关/Ingress/Nginx 是否能连到 Web/Server。
3. 查 Web 容器是否运行、端口是否监听。
4. 查 Server 容器是否运行、`/healthz` 是否正常。
5. 查 Server 日志是否有上游不可达、数据库不可达、Agent 不可达。
6. 查最近部署镜像版本是否正确。
7. 查 DNS/CDN/证书是否异常。

常见原因：

- 容器未启动或 crash loop
- 端口映射错误
- 网关 upstream 配错
- Server 无法连接数据库/Redis/Agent
- 镜像拉取失败或部署没有替换旧容器

### 4.3 接口 500 排查

检查顺序：

1. 浏览器 Network 记录：URL、method、status、response body、request payload。
2. Server 日志按时间点搜索错误。
3. 确认是否为认证问题：cookie/satoken/KYC/权限。
4. 确认数据库迁移是否完成。
5. 确认外部 Java 接口是否返回非 200 envelope。
6. 确认 AI Provider / Agent / Redis 是否异常。
7. 如果是新部署后出现，优先对比最近 commit 和环境变量。

### 4.4 数据库 / Redis 排查

Postgres：

- 容器/实例是否健康
- `DATABASE_URL` 是否正确
- 用户名密码是否匹配当前 volume/实例
- Prisma migration 是否成功
- 是否存在 failed migration
- 连接数是否打满
- 磁盘是否满

Redis：

- Redis 是否运行
- `REDIS_URL` 是否正确
- 内存是否满
- BullMQ 队列是否堆积
- Pub/Sub 是否正常

### 4.5 Agent / AI Provider 排查

检查顺序：

1. Agent 容器/Pod 是否运行。
2. Server 到 `MASTRA_URL` 是否可达。
3. Agent 日志是否启动完成。
4. Redis 队列是否堆积。
5. Provider API Key 是否有效。
6. Provider 余额/额度/区域限制是否异常。
7. 模型参数是否被错误配置。

### 4.6 部署失败排查

检查顺序：

1. CI/CD 是否成功构建镜像。
2. 镜像 tag 是否推送到正确 registry。
3. 服务器是否 pull 到新镜像。
4. compose/k8s 环境变量是否使用正确 env 文件。
5. 数据库 migration 是否执行成功。
6. 新容器是否替换旧容器。
7. 健康检查是否通过。
8. 回滚方案是否可立即执行。

## 7. 活动/教育场景保障

### 7.1 事前

- 确认活动入口、课程页面、支付/积分、登录、AI 生成、内容访问链路。
- 确认余额、API 额度、短信/邮件额度。
- 确认当天值班人和备用人。
- 确认回滚方案和降级方案。
- 活动开始前 24 小时、2 小时、30 分钟分别做一次健康检查。

### 7.2 事中

- 监控错误率、响应时间、登录失败率、关键接口成功率。
- 一旦 P0/P1，先止血，再定位。
- 5-10 分钟内给群里和邮件同步第一版状态。
- 必要时暂停非关键入口，保核心活动流程。

### 7.3 事后

- 记录影响范围、恢复时间、根因、处理动作。
- 输出复盘邮件。
- 更新 SOP、权限表、告警阈值。
- 如果是权限问题，必须补齐第二负责人。
- 如果是余额/额度问题，必须补自动充值或低余额预警。
