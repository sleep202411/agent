## Payment findings and integration repairs

The incoming paywall referenced undeclared `router`, `toHref`, `ActivityIndicator`, and `notifyUnavailable`, and its parameter type omitted `returnPath`. The combined branch restores the intended purchase and web-continuation handlers, imports and router initialization, and disables purchase while an action is pending. Four incoming components also used icon paths that did not resolve to installed runtime files; they now use supported named package exports. Three mocked component tests cover purchase dispatch/pending state, return-path web continuation, and the WeChat catalog-loading state.

These repairs do not establish payment correctness:

- `apps/mobile/src/features/paywall/lib/storekit-iap.ts` finishes a matching-SKU transaction before a verified account-linked backend fulfillment step. The inspected flow returns the product ID, has no app-account token mapping or durable pending fulfillment queue, and restores through the SDK. Receipt validation, server-side order/grant contracts, idempotency, refunds, account changes, app-close recovery, and restore acceptance must be specified and implemented/tested before release. External Java backend behavior was not inspected.
- `wechat.ts`, `billing-api.ts`, and `wechat-scan-pay.tsx` implement Native QR checkout through Nest billing, not WeChat App SDK payment. Verify same-device QR usability, paid versus fulfilled order states, wallet refresh, account changes, and recovery. Do not substitute SDK integration assumptions for this actual flow.
- `package.json` declares IAP `^16.6.1` and Nitro `^0.37.1`. The lock contains Nitro `0.36.5` and mobile `0.37.1`, while the IAP entry declares a `^0.36.5` peer. The local dependency inspection returned no installed IAP dependency, and `apps/mobile/ios` is absent. Reconcile the native dependency graph and follow `apps/mobile/BUILD.md` for a development build; a JavaScript test run cannot verify native linking.
